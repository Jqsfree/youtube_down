# youtube_down 渐进改进方案

日期：2026-10-30。基线：当前工作区 v1.3.1。状态：第五批代码与双平台构建验收通过；第一批真实升级验证仍为发布前待办。

## 1. 架构判断与目标

这是一个已有 GUI、CLI、活动队列、断点续传和双平台分发的桌面工具。当前主要问题是安全边界不够明确，以及下载编排夹在 Qt worker 中，导致复用和验证成本增加。根目录平铺本身不是首要问题。

采用“先修风险、再建立可重复验证、最后按职责拆分”的路线。保留 PySide6、yt-dlp、现有入口和平台插件，不预先承诺 v2.0 或全面目录迁移。

其他路线的取舍：仅修补现有代码投入少，但 GUI/CLI 编排重复仍会积累；一次迁入 src/ytdown 并引入完整分层会同时影响打包、入口、测试和运行行为。本方案先拆出有明确调用方的职责，包布局迁移另行判断。

完成后的直接收益：更新不再因缺失校验信息而放行；浏览器 Cookie 不再默认整库持久化；发布依赖可追溯；GUI 与 CLI 能复用批量执行规则。

## 2. 已核实的基础

- build.yml 已有单元测试和联网 smoke test；缺的是 PR 检查、发布隔离和依赖固定，不是完全没有 CI。
- main 推送会发布，draft=false，允许覆盖已有资产；安装依赖后还会升级 yt-dlp，构建没有严格采用锁文件。
- app_updater.download_update 在清单或对应条目缺失时仍返回下载结果。
- downloader 初始化在 macOS 可能导出浏览器 Cookie；dump_browser_cookies 没有目标域名过滤和显式权限设置。
- 引擎 overlay 已使用 PyPI wheel 与 SHA256，并同时更新 yt-dlp、yt-dlp-ejs。
- worker 包含队列、重试、并发、续传及记录逻辑；浏览器 Cookie 模式已有降为单 worker 的保护。
- tests 已覆盖上述多个行为，应在原测试文件中补用例，避免重建一套平行测试体系。

依据为本次源码阅读；未运行测试、下载、安装或平台演练。外部签名服务、费用及许可义务不在本次核实范围。

## 3. 必须保持的行为

- python main.py、youtube-down、youtube-down-cli 继续可用。
- GUI 不导入 yt_dlp，纯逻辑模块不导入 PySide6。
- 默认无 Cookie 下载，仅按现有错误类别触发 Cookie 重试；保留显式 Cookie 覆盖和浏览器锁库保护。
- 活动队列可在运行时入队；取消能唤醒等待；暂停仍在当前任务结束后生效。
- 输出目录、媒体命名、下载总览.csv 列与键保持兼容，历史结果只读兼容。
- 不自动迁移或删除用户 Cookie、历史下载和配置。安全修补引起的行为变化在 CHANGELOG 和界面中明确说明。
- 修改运行脚本前检查进程；不得覆盖正在执行的文件。每批独立提交，不混入格式化全仓或目录搬迁。

## 4. 第一批：Cookie 边界与更新放行条件

建议拆成三个独立变更，按顺序实施。

### 4.1 Cookie 默认行为与生命周期

涉及 downloader.py、worker.py、gui.py、download_cli.py，以及 Cookie 相关测试和 README。

1. 取消 macOS 初始化自动导出。浏览器读取必须由用户明确选择；复用已有 Cookie 选择入口，补充凭据提示。
2. 正常浏览器模式直接交给 yt-dlp 读取。确需导出时复用平台域名配置，创建应用拥有的临时副本；过滤域名时使用精确域名或点分隔后缀，不能用任意字符串包含。
3. POSIX 临时文件创建即为 0600；Windows 使用当前用户私有位置并验证实际访问控制，不能把 chmod 当作 Windows ACL 保证。
4. 显式传给 yt-dlp 的 cookiefile 使用应用副本，避免库保存 cookiejar 时改写用户原文件。用户原文件的内容、权限和位置均不改动。
5. 下载器持有副本直到相关并发任务全部结束，在成功、失败、取消和正常退出路径清理。崩溃残留只清理应用私有临时目录中可确认归属且未被使用的文件。
6. 旧 auto_browser_cookies.txt 不自动沿用；给出说明和明确清除入口，不扩展为扫描用户目录。

验收：构造包含三个平台与无关域名的假 Cookie；验证过滤、权限、异常与取消清理、并发共享期间不提前清理、用户原文件不变。测试不得访问真实浏览器或记录真实凭据。GUI/CLI 的导入和逐条覆盖均需覆盖。

### 4.2 更新校验失败即停止

涉及 app_updater.py、tests/test_app_updater.py、更新界面文案。

1. 先取得清单并确认目标条目有效，再下载目标资产；缺失、解析失败、重复冲突条目、摘要不合法均拒绝。
2. 下载仍保留域名和重定向限制、大小及摘要校验；失败时不进入安装脚本，清理本次临时文件。
3. 说明这能拦截损坏和不完整发布，不能证明发布账号未失陷。签名清单单独设计。
4. 现有资产名称不变。仅增加系统/CPU 兼容检查，不顺带提供新架构产物；无法确认支持时提供手动下载入口。

验收：无清单、无条目、坏摘要、下载截断、重定向越界、校验通过各有测试；验证所有失败分支均不调用安装。

### 4.3 文件匹配与安装脚本

涉及 downloader.py 文件暂存/恢复相关函数、app_updater.py 安装脚本生成及对应测试。

1. 文件匹配优先遍历目录并比较字面文件名；若使用 glob，只对动态文件名部分转义。不能只修一个 glob 而遗漏同一恢复链上的匹配。
2. macOS 路径以安全引用或位置参数传入；Windows 审查批处理中的百分号、感叹号和引号展开，必要时换成参数化辅助脚本。不能以普通双引号视为已完成防注入。
3. 保留替换失败回滚。尚未实现启动健康回滚时，文档必须明确二者区别。

验收：带空格、中文、方括号、引号和 shell 元字符的合法平台路径；匹配不影响相邻文件；替换失败可恢复。脚本生成测试之外，Windows/macOS 各做实际安装演练后才发布相关修改。

## 5. 第二批：把发布与日常开发分开

涉及 .github/workflows/build.yml、依赖声明、tests/test_release_consistency.py、BUILD.md、AGENTS.md、CHANGELOG.md。

1. PR 与 main 的普通提交运行离线测试；已有联网 smoke test 移至定时和手动任务。真实站点故障不应阻塞纯本地修复的验证。
2. v* tag 或明确的手动发布触发构建；校验 tag、VERSION、pyproject 三者一致。暂不为消除一个重复字段引入复杂版本插件。
3. 发布权限只给 release job；构建使用只读权限。相同版本禁止覆盖已发布资产；失败发布用新补丁版本恢复，不修改历史产物。
4. 创建 draft release，完成资产和校验清单检查后由维护者发布。至少记录 Windows/macOS 的启动、下载、更新结果。
5. 以 pyproject + uv.lock 管理发布依赖；先验证锁文件可在两个平台解析和安装，再让 CI 严格采用锁文件。requirements.txt 若继续提供，则由同一来源生成并在 CI 检查同步。移除构建时无约束的 pip install -U。
6. 外部 ffmpeg/ffprobe/deno 的版本、来源、摘要随构建记录；先锁定已验证组合，再单独更新。打包后验证工具能启动，避免只验证源码环境。

验收：普通 PR 不创建 release；错版本 tag 被拒绝；draft 包含双平台资产及各自校验条目；不可覆盖同版本；依赖清单可追溯。流水线改动先手动构建验证，再启用正式发布。

文档同步：AGENTS.md 当前写明 main 自动发布，必须同步修改；BUILD、README 与生成的 release 文案也必须一致。

## 6. 第三批：增加故障证据，不暴露凭据

涉及 logger_utils.py、gui_log.py、downloader.py 的 yt-dlp logger、GUI/CLI 日志调用和测试。

- 复用现有 AppLogger 增加轮转和保留上限；先定义日志字段，再接通 yt-dlp 输出。
- 正常日志记录版本、平台、任务阶段和错误类别。下载 URL、代理用户信息、Cookie 路径及 token 默认脱敏；原始响应、HTTP 请求头和 Cookie 内容不进入日志。
- 用本地任务编号串联过程，不把新的 Job 状态机作为日志前提。
- 第一版只提供“打开日志目录”，诊断压缩包等到有实际支持需求再做。
- 错误分类先补真实脱敏样本和 ffmpeg/ffprobe/deno 缺失规则；仅在已有可靠信号时使用异常类型和 HTTP 状态，保留关键词兜底。

验收：用假凭据验证普通日志与异常路径均不泄露；错误分类测试验证优先级；检查日志轮转和磁盘写入失败不会使下载崩溃。

## 7. 第四批：按职责减少 downloader 的改动面

只在前三批稳定后开始，每次只拆一个职责，不改变入口或包布局。

建议次序：cookies.py（Cookie 副本与来源管理）→ media_probe.py（工具解析、ffprobe、媒体验证）→ download_errors.py（类别与规则）。文件名实施前检查与现有模块是否冲突。

downloader.YoutubeDownloader 的公开方法和原有导出先保留，内部委托给新模块。GUI/CLI 无须同时更换调用方式。每个新模块保持无 PySide6；Cookie 或引擎所需的 yt_dlp 接触点按实际职责约束，不强行规定只有一个目录可以导入。

每次拆分先确认已有测试覆盖输入、输出、异常与副作用，再搬代码；不得同时调整策略。补简单的导入边界检查即可，暂不新增 import-linter、pyright 等成套门禁。ruff 可先在改动文件启用，避免历史格式问题扩大范围。

验收：原公开接口测试及对应新模块测试通过；GUI/CLI 导入和打包通过；输出、错误类别、Cookie 策略无未说明差异。行数只用于发现职责混杂，不设 600 行硬门槛。

## 8. 第五批：让 GUI 与 CLI 共享批量执行规则

这是本方案风险最高的一批，必须单独实施，不能与前述搬迁合并。

先对照 worker.py 和 download_cli.py，列出格式回退、Cookie 重试、续传、节流和 CSV 记录的实际差异；区分有意差异与重复实现。只有共同部分进入纯 Python batch_runner.py。

最小边界：runner 接收下载器、任务输入、取消/暂停控制和结果回调，不导入 Qt。保留现有结果字段；不先引入事件总线、FileSystem/Clock 通用端口或新的持久化格式。

迁移顺序：单条任务执行与重试 → 顺序批量 → 活动队列 → 并发执行。worker 保留 QThread 和 Signal 适配；CLI 调用同一执行核心。每步通过后再迁下一步。

验收必须覆盖：空队列、运行中入队、入队与退出同时发生、重复任务、等待时取消、暂停后继续、Cookie 首次失败与重试、浏览器锁库、结果记录失败、恢复已完成文件、并发完成顺序不同。使用 FakeDownloader 和可控制的同步点，避免依赖真实下载或固定 sleep。

并发第一版保留现有安全限制，集中管理 worker 数和分片数，明确它们仅是并发配置而非所有 HTTP 连接的硬上限。保留浏览器 Cookie 单 worker 保护。新的数值上限和动态恢复算法在测得吞吐、429、风控结果后单独决定。

## 9. 验证与发布节奏

每个变更先补能复现目标问题的用例，再修复，再运行相关测试，最后运行全量测试：

```bash
QT_QPA_PLATFORM=offscreen python -m pytest tests/ -q
```

该命令是计划中的验证命令，本次未执行。执行前需确认本地 Python 与依赖环境。联网测试拆分后，默认测试集只运行离线用例。

第一批安全修补和第二批发布隔离完成后，可安排 v1.3.2；外部签名申请不阻塞该补丁，但没有实际平台验证的安装脚本改动不能混入发布。第三批稳定后安排下一补丁。第四、五批根据兼容性决定后续小版本，不预先用版本号推动范围。

源码提交可逐批回退；公开发布后通过新版本修复，不重写旧 tag 或资产。用户数据和 CSV 格式不迁移，避免回退时需要反向转换。Cookie 默认安全策略不因回退便利而重新开启。

工期先只估算前两批：约 5–9 个有效开发日，加双平台演练与等待时间；这是假设已有环境可用的工作量估计，不是交付承诺。完成基线测试和第一批后再估算后续批次。

## 10. 后续专项与外部决策

- 签名更新：先明确威胁模型、密钥存储与轮换、旧客户端过渡、防降级规则，再实现签名 manifest。不得把同源 SHA256 当作身份认证。
- 启动健康回滚：设计外部监护进程/脚本、健康检查范围、超时和回滚后启动行为；明确它只能处理约定的启动故障，不能承诺任意运行故障自动恢复。
- overlay：保留 PyPI wheel 路线，验证 yt-dlp/ejs 版本组合，在独立进程中执行导入与版本自检，失败回退内置版本；不能在已加载模块的进程内证明新版本可正常启动。
- 代码签名费用、应用许可证、Intel Mac/Linux 支持，需要负责人决定。未决定前，不新增相关发布承诺；许可证与第三方分发义务单独核查。
- src 布局、第三方插件、i18n、队列持久化和配置目录迁移，只在具体需求出现后立项，不列入当前必做验收。

## 执行记录

第一批验收标准（执行前冻结）：Cookie 默认不导出、不读取未选择的浏览器；显式导入原文件不被 yt-dlp 改写；临时副本仅包含目标域且正常/异常/取消后清理；无有效校验清单不下载或安装；特殊文件名不误匹配；安装脚本路径不被解释成命令。自动化测试全绿，Windows/macOS 实际安装演练均通过后才算整批验收通过。未通过不得进入第二批。

基线：解除沙箱限制后 265 passed；沙箱内的 13 个失败为本地端口/Downloads 日志写入权限。工作分支 architecture-batch-1。使用现有目录，避免工作树搬迁增加环境差异。先处理独立的校验清单与文件匹配，再处理 Cookie 生命周期。

### 第一批执行结果（尚未整批验收）

- 已实现：默认不选择浏览器；每次 yt-dlp 操作使用独立、按媒体平台过滤的 Cookie 副本；CLI 显式浏览器导出使用独立快照，退出时清理；禁止导出覆盖已有文件；POSIX 私有权限及 Windows 当前用户 ACL；校验清单先检查后下载，缺失/冲突拒绝；不支持 CPU 的运行环境不选择更新包；文件名 glob 转义；PowerShell 使用 JSON 路径数据；macOS 安全引用路径。
- 测试证据：本次基线 265 passed；新增问题测试先失败后修复。最后全量测试 285 passed，使用 `QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest tests/ -q`，因已有 GUI 测试写 Downloads 日志及本地 socket 测试需要，使用已批准的沙箱外执行。最终日志 `/private/tmp/ytdown-baseline-unrestricted.log`，原始基线 `/private/tmp/ytdown-original-baseline.log`。日志是本机临时证据，不纳入版本库。
- macOS 在临时目录用假解压/启动命令测试了安装成功、复制失败回滚及特殊路径无命令执行；这不是完整 `.app` 升级演练。
- 独立审查发现：CLI 无 Cookie 且换节点失败时错误清零风控计数。已补端到端编排测试先失败后修复，验证退避和两次连续风控熔断。
- 调整理由：Cookie 副本按每次 yt-dlp 调用持有，CLI 导出快照按会话持有，避免依赖 GUI 退出时机，也避免并发提前删除。未自动清理历史文件或崩溃残留，README 提供明确路径与清理条件，防止误删其他进程仍使用的文件。
- 同步了 README、BUILD、CHANGELOG、AGENTS 和 pyproject 模块清单。没有改版本号、构建或发布流程，没有提交或发布。
- 待验收：Windows 真实 ACL、PowerShell 成功/占用重试/失败回滚及特殊路径安装；Windows/macOS 打包产物真实升级。当前仅 macOS 主机，没有 Windows 实际执行证据。
- 审查暂缓小项：macOS 安装脚本目录和提取失败路径的临时目录可能残留。仅包含安装文件，不包含 Cookie；后续清理时必须避免删除运行中的安装目录。

结论：第一批代码与本机自动化验证完成，但整批验收未通过；第二至第五批未启动。需要补齐上述跨平台运行证据，不能将脚本内容检查或模拟安装替代真实升级。
