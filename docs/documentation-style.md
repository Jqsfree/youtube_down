# Markdown 文档维护规范

目标：保证用户快速找到**当前可信且可执行**的信息，降低随着代码变更出现的文档漂移。

## 信息架构

- 根目录 [README](../README.md)：一句话定位、已发布版本/平台、五分钟启动、核心功能与限制、文档导航。避免复制完整 CLI 帮助和构建流程。
- [usage.md](usage.md)：用户操作、真实参数、输入输出、权限边界。
- [troubleshooting.md](troubleshooting.md)：症状 → 可能原因 → 最小验证 → 处理和收集证据。
- [development.md](development.md)：本地环境、测试层级、发布门槛、可执行命令。
- [architecture.md](architecture.md)：现有职责/依赖、业务数据流、差异与约束。
- [BUILD.md](../BUILD.md)：构建工具、发布工艺与依赖细节；[AGENTS.md](../AGENTS.md)：供 Agent 执行的限制及验收规则。
- [CHANGELOG.md](../CHANGELOG.md)：按版本记录行为变化；[architecture-plan.md](architecture-plan.md) 是历史过程记录，保留日期但不重复作为现状文档。

## 每个章节的写法

1. 先给结论或使用场景，随后给步骤或代码，最后写限制与验证信号。
2. 事实必须有对应源码入口、实际 CLI `--help`、GitHub workflow 或具体运行结果。没有证据写「待验证」，不写「已支持/已完成」。
3. 区分 `main`、PR、草稿和已发布安装包；后者只包含对应 tag 的代码。标记最后核对日期。
4. 命令示例可直接复制，指定运行目录和操作系统。不得把 Linux shell 命令写成 Windows PowerShell 通用命令。
5. 面向用户的文本优先问题导向；不要用全是类名、函数名的列表替代如何操作。开发文档必须写可检查的成功/失败信号。
6. 保留必要的安全边界：Cookie、个人账户、代理凭据不进仓库或报告；下载受内容权限及平台约束。
7. 每一项默认值只在一处详述，其他地方链接引用。代码改变时，应同时更新对应权威页和 Changelog。
8. 不夸大性能和覆盖率；不要写「99% 成功」等无测量来源的数据。

## Markdown 约定

- 每份文件一个 `#` 顶级标题，按 `##`/`###` 顺序递进。
- 单独段落表达一个结论；长文使用短小小节和必要的表格，避免大段重复。
- 代码块标注语言（`bash`、`powershell`、`text` 等）；路径优先使用仓库相对路径。
- 链接使用相对 Markdown 路径，外部参考提供指向官方源码、文档或稳定页面的链接。
- 引用别的项目的**文档组织方法**，不要直接复制对方大段 README 或未经验证的功能声明。
- 版本依赖保留 `pyproject.toml` / `uv.lock` 作为来源，历史运行结果附 commit SHA 与 Actions run。

## 更新检查清单

- [ ] 功能和参数与当前代码对应，已发布安装包的版本未混淆
- [ ] 所有新增内部链接可以在仓库解析，标题/锚点有效
- [ ] 命令、默认值、平台限制与可复制性已检查
- [ ] 新增功能和修复同步到 CHANGELOG 的 Unreleased
- [ ] 若涉及行为/风险，已更新故障排查或验收文档
- [ ] 没有 Cookie、Token、密码和私人 URL
- [ ] 外部资料链接可访问并注明借鉴范围

## 借鉴项目（只借鉴结构与解释方式）

- [yt-dlp](https://github.com/yt-dlp/yt-dlp)：明确安装方式、CLI 选项及输出模板/示例；参数资料与故障知识作为上游参考，不能直接视为本工具已支持。
- [MeTube](https://github.com/alexta69/metube)：README 放快速开始和配置入口，详细 recipes 与 FAQ 单独组织，区分 UI 与引擎故障。
- [Tartube](https://github.com/axcore/tartube)：对实际发行平台、安装包、使用教程和支持边界分开说明。

遵循本仓库的使用者与技术栈，不照搬其他项目的容器部署、服务端配置或跨平台支持承诺。
